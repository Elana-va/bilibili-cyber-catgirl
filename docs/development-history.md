# 开发历程：从一个账号截图到安全可控的 AI 角色系统

这份记录还原 Bilibili Cyber Catgirl 的真实开发过程。项目不是按一张完整蓝图一次完成，而是在持续提问、验证和收紧边界中形成的。

## 起点：发布内容的“不是人”是怎么实现的

项目源于一个 B站账号截图：账号以猫娘身份持续发布动态、阅读评论并互动，看起来像一个由大模型驱动的虚拟角色。

最初的问题很直接：这种系统是怎么实现的？拆解后，我们发现它至少包含五层：模型负责理解和生成，人设负责保持口吻，平台连接器负责读取与写入，调度与数据库负责持续运行，安全与人工审核负责避免模型直接伤害主账号。

我们没有采用“模型加一组工具即可随意操作账号”的演示型结构。那种方式上手快，却很难证明它不会重复回复、误发内容或在提示注入后执行不该执行的动作。

## 第一个路线决定：先做 B站

讨论过微信、抖音和小红书后，我们决定先把 B站闭环做成熟，再迁移通用能力。目标账号、公开内容和评论场景明确，适合先验证完整链路：

```text
发现内容 → 读取评论 → 理解上下文 → 生成人设回复
→ 风险判断 → 人工审核 → 安全发布 → 结果审计
```

这也确立了第一代边界：不做直播、私信、多账号、群控和验证码绕过。

## 2026-07-14：安全基线先于功能

仓库在 7 月 14 日初始化。最早确定的不是 UI 或猫娘台词，而是三个原则：默认全人工、关键动作可审计、任意时刻可紧急停止。

它们意味着“自动化”不是默认状态，而是需要多个条件共同放行的受控能力。

## 2026-07-15：从领域骨架到完整控制台

7 月 15 日是主要建设阶段，共形成 55 个小步提交。每个能力先定义边界和测试，再逐步连成系统。

### 1. 领域模型与持久化

首先定义事件、草稿、发布任务、消息、记忆、审计日志和每日指标等核心对象，并使用 SQLAlchemy、Alembic 和 SQLite 持久化。

这一阶段重点解决两件事：同一评论被多次读取不能产生多个草稿；服务重启不能丢失分页位置和待处理任务。因此事件 ID、检查点和发布幂等键从一开始就有唯一约束。

### 2. Agent 不是发布器

我们接入 DeepSeek 的结构化输出，却没有让模型直接调用 B站工具。Agent 只返回受 JSON Schema 约束的决策对象，安全服务再决定忽略、送人工审核还是进入有限自动流程。

同时加入用户级历史、低敏感记忆、敏感信息拒绝和提示注入防护。模型可以记住内容偏好，但不应该记住密码、住址或支付信息。

### 3. 本地审核台与 UI 重构

第一版后台只是朴素的待审核列表。随着监控、内容计划、分析和设置增多，我们重新设计完整管理台：桌面侧边导航、移动端底部导航、状态卡、风险徽章、统一空状态，以及工作台、评论监控、审核、内容、分析、日志和设置七个页面。

UI 的目标不是单纯“更像 AI 产品”，而是让运营者一眼看清：当前是否在读取、是否允许写入、是否存在异常、下一步会不会影响真实账号。

### 4. B站扫码登录与凭证保护

账号通过手机 App 扫码确认。Cookie 不进入网页、SQLite 或源码，而是在 Windows 上使用 DPAPI 加密到本地文件；连接后先执行只读身份探针，让用户核对昵称和 UID。

扫码成功只代表身份建立，不代表评论监控或写入自动开启。

### 5. DeepSeek 可视化连接

设置页随后加入 DeepSeek 连接卡片。API Key 先经模型列表接口验证，成功后再加密保存；失败信息经过清洗，避免上游错误把密钥带回页面或日志。

这一阶段也修复了连接表单重叠、密钥回显和模型响应兼容问题。

### 6. 评论监控与历史回溯

评论监控从“读取一个视频”扩展为自动发现近 30 天视频与动态、读取顶级评论与楼中楼、分页回溯历史、持久化游标、重启恢复和平台限流退避。

用户特别提出“账号之前的评论也要回复”，因此历史回溯成为正式能力，而不是只监听启动后的新评论。第一代仍要求所有历史回复经过人工审核。

### 7. 为未来自动回复保留通道

项目最终选择“人工审核是主流，但保留有限自动通道”。自动回复具备白名单、频率限制、随机延迟、风险等级和独立写入开关，默认全部关闭。

这让系统以后能从人工试运行平滑升级，而不必重写 Agent、数据模型和审核流程。

### 8. 真实连接后的可靠性修复

真实账号暴露出模拟环境看不到的问题：身份响应变化、评论结构差异、调度任务重叠、模型 Schema 兼容、平台风控和写入恢复。

对应修复包括兼容身份响应、修复实时同步、串行化内容发现任务、风控后停止写入，以及在服务层再次执行安全闸门。这说明安全不能只依赖 UI 按钮，关键约束必须在运行时重复验证。

## 2026-07-16：猫娘从提示词升级为契约

初版角色只要求“像猫娘一样回复”。实际运行后出现了称呼不稳定、颜文字重复、所有场景语气相同等人设漂移。

我们重新确定人设：亲和、活泼、俏皮和赛博感提高；默认称呼“小伙伴”；偶尔称呼“主人”；更常使用颜文字；说话自然带“喵”。

这些要求被写成 `catgirl-v2` 人设契约，并加入确定性校验和近期风格历史。回复不仅要“像”，还要能解释为什么通过或失败。

### 49 条历史草稿的重生成

人设上线后，我们对已有 49 条评论草稿重新生成。过程中暴露出三个工程问题：

1. 临时 Python 运行环境变化导致 HTTP 客户端依赖失效；
2. DeepSeek 偶发读取超时，批量并发放大失败概率；
3. 第一轮有 13 条生成成功但未通过人设校验。

处理方式是先做 SQLite 在线备份，切换到项目自己的 `.venv`，再以小批次生成。遇到超时立即停止、恢复对应旧草稿并降低并发。13 条失败项按来源事件逐条纠偏，最终 49 条均成为 `catgirl-v2` 待审核草稿，且没有产生发布任务。

这次经历反过来验证了最初的设计：有备份、有来源关联、有审核状态、有写入闸门，模型失败才不会变成账号事故。

## 我们学到的东西

### AI 角色系统的难点不在“会说话”

模型生成一句可爱回复很容易，持续、相关、不重复、可恢复且不误发才是系统工程。

### 人设需要可验证

只写提示词无法保证长期一致。稳定角色需要版本化契约、确定性规则、近期风格历史和失败路径。

### 真实账号必须默认拒绝写入

授权、运行模式和自动回复应该是独立开关。即使 UI 出错，服务层仍要阻止未经授权的写入。

### 批量任务要为部分失败设计

模型超时和平台限流是正常事件。批量操作必须支持小批次、断点恢复、幂等和保留旧结果。

### 平台能力应该隔离在连接器

Agent、人设、安全、审核和审计可以跨平台复用，登录、评论结构和发布接口则由连接器承担。

## 下一步

当前优先级不是扩大自动化，而是提高可观察性、批量重生成的事务安全和平台接口稳定性。未来接入新平台，也会沿用“连接器可替换、生成不等于授权、默认人工审核”的原则。
